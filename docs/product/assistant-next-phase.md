# Assistant: plan for the real-time phase

Prepared 2026-11-11 from the code as it stands (`BackEnd/.../assistant/`, `FrontEnd/src/app/features/assistant/`) and ADR-012. Nothing in this document is built yet. Items marked **Decision** need the owner's approval before work starts.

## Where it stands today

| Topic | Current state |
|---|---|
| Provider | None. `app.assistant.mode` is `disabled` by default and `demo` under the demo profile. `demo` is a deterministic local adapter (`DemoAssistantModel`); answers are labelled as not generated by a live model. `live` is reserved and behaves as unavailable (ADR-012). |
| Who may use it | BUYER and PURCHASING_MANAGER only (`ASSISTANT_USE`). Everyone else gets 403; supplier contacts are refused explicitly. Verified: GLOBAL_ADMIN and a requester both receive 403 on `/api/v1/assistant/status`. |
| Data scope | Retrieval runs on the server through the same services the screens use, as the signed-in user, before any prompt is assembled. The model never writes SQL, URLs or code. A request can be named by reference to narrow the question. |
| Abilities | Five intents: find, explain, summarise, draft, help. A draft is text for a supplier message, labelled "Draft — not sent"; the assistant sends nothing and changes nothing. |
| History | Threads and turns are stored per user and company (`AssistantStore`). The screen shows only the latest answer. No retention period is defined. |
| Transport | One `POST /api/v1/assistant/ask` that returns the whole answer. No streaming, no cancel. Rate limit per user and per address (default 30 a minute), a timeout (20 s) and a maximum question length. |
| Safety | A small phrase filter for prompt injection. Audit records outcome, mode, duration and source ids, not the text. |
| Screen | A form (request reference, question, starter chips), a "thinking" line, the answer as plain preformatted text, sources as links, and the draft. It takes the Meridian look from tokens but has no conversation layout. |

## Proposed for the next phase

### 1. Provider (**Decision**)

Keep the `AssistantModel` port and add one live adapter. Recommendation: Anthropic's Claude API, called from the backend only, starting with `claude-sonnet-5-5` for answer quality in French and Arabic, with the model id in configuration. This is ADR-012's option B, so it needs what that option lists: a data-processing agreement, a retention and residency review, and the key in the secret store. If data may not leave the network, option A (a self-hosted endpoint behind the same port) is the alternative, with answer quality in Arabic to be proven first.

The ADR needs an amendment recording the choice. `demo` stays the default for tests and local work.

### 2. Transport (**Decision**)

Server-Sent Events over a `POST` that returns `text/event-stream`, read in the browser with `fetch` and a stream reader. Why: answers flow one way, it works through the existing session cookie, CSRF token and proxy, and it needs no new infrastructure (ADR-003). WebSockets would add a second authenticated channel for no gain here.

Events: `sources` (what was retrieved, sent first), `delta` (text), `draft`, `done` (turn id, duration), `error` (a problem code). The existing non-streaming endpoint stays for tests and as a fallback.

### 3. Roles and scope

No change to the rule that retrieval is authorised before the prompt. Open question for the owner: extend use beyond buyers.

| Role | Proposal |
|---|---|
| Buyer, purchasing manager | As today |
| Requester | Own requests only: "where is my request, who has it, what is missing" |
| Approver | Requests in their queue: summary and what the decision covers |
| Receiver | Orders they may receive |
| GLOBAL_ADMIN, supplier contact | No access |

Each extension needs its own retrieval allowlist and a cross-company test, as every endpoint does.

### 4. Explain only, or propose actions (**Decision**)

Recommendation: explain, find and draft in the first live release, exactly as today. In a second step, allow **proposals that the person confirms**: the assistant returns a structured proposal (for example "assign to buyer X", "open an RFQ for supplier Y") and the screen shows it as a card with the ordinary confirmation dialog. The action then goes through the existing endpoint as the user, with the existing permission, validation and audit. The assistant never executes anything itself, and nothing irreversible is proposed without the dialog.

### 5. Conversation history and retention (**Decision**)

- Show the thread: the stored turns are already there; add `GET /assistant/threads/{id}`.
- A thread list in a side column, newest first, titled by the first question.
- Retention: propose 90 days, then deletion by the existing job runner; a person can delete their own thread at once. The period and whether threads count as records are the owner's call, with the privacy review of point 1.
- Full prompts stay out of the logs, as today.

### 6. Streaming, cancellation, waiting and failure

| State | Behaviour |
|---|---|
| Sent | The question appears at once; the composer is disabled; a "Stop" button replaces "Ask" |
| Retrieving | "Reading the request…" with the sources appearing as they are known. No fake typing |
| Streaming | Text appears as it arrives; one polite live region announces completion, not every word |
| Stop | Aborts the request; the partial answer is kept and marked as stopped |
| Timeout or network loss | The partial answer stays, marked incomplete, with "Try again" for that turn |
| Rate limit (429) | Says when asking is possible again |
| Provider unavailable | The page stays usable; the reason is stated, and search and the record remain reachable |
| Refused by scope | Says the request is outside what the person may see, without confirming it exists (404 behaviour) |

### 7. Layout in Meridian

- Two columns from 64 rem: thread list (collapsible), conversation. One column on phones, with the thread list as a drawer.
- Solid surfaces for the conversation; glass only for the composer bar that floats at the bottom.
- The person's turn at the end side on a soft accent surface; the assistant's turn full width on the surface, with source chips under it that open the record.
- A draft or a proposal is a card with its own actions ("Copy", "Open in messages", later "Confirm…").
- Answers render a safe subset of Markdown (paragraphs, lists, emphasis, links to in-app paths only). Today's preformatted block goes.
- The mode badge stays visible: "Demo" or the provider's name.
- Arabic: turns mirror; reference numbers stay left to right in `<bdi>`.
- Reduced motion: text appears in whole paragraphs.

### 8. Work to schedule

1. ADR-012 amendment (provider, retention) and the privacy review.
2. Backend: streaming endpoint, live adapter, thread read endpoint, retention job, tests with the provider stubbed.
3. Frontend: conversation component, stream reader with abort, thread list, Markdown subset, states of point 6, EN/FR/AR strings.
4. Evaluation set: fixed questions in three languages with expected sources, run before each model change.
5. Security review: prompt-injection cases through record text and supplier messages, and cross-company retrieval.

Out of scope until decided: role extensions (point 3) and confirmed proposals (point 4, second step).
