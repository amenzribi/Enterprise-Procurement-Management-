# Sprint 0 Design Review

- Reviewer: Reviewer agent (independent)

- Scope: `docs/analysis/*`, `docs/decisions/*`, `docs/architecture/architecture.md`, `docs/product/*`, `docs/qa/*`,

Severity: **Blocker** = must be resolved before the affected sprint starts · **Major** = will cause rework or a
failed acceptance if ignored · **Minor** = fix when touching the area · **Suggestion** = optional.

## Findings

| ID | Severity | Reference | Finding | Recommended action |
|---|---|---|---|---|
| DR-01 | Blocker (for S1) | ADR-007; architecture §5; mvp.md | Isolation is modelled as "every company-scoped row has `company_id`, user sees own company". But a request involves up to four companies (§3.2: requesting, charged, buying, plus the central purchasing company that processes it, §3.7, §8). The central purchasing team *must* see other companies' validated requests, and "on behalf" purchases are issued in the subsidiary's name. A single `company_id` filter either breaks the central inbox or leaks data. | Before S1, write a visibility model: which company columns a request carries (`requesting_company_id`, `charged_company_id`, `buying_company_id`), and per role which column(s) grant access and from which status (e.g. central purchasing sees requests where `buying_company_id` ∈ scope *and* status ≥ "Validée"). Add it to ADR-007 and make S1-AC-07 test it. |
| DR-02 | Major | ADR-007 | "Repositories and queries take the scope explicitly" relies on every developer remembering every query (lists, counts, exports, dashboards, search, document download, audit history). One omission = cross-company leak, the highest-impact defect class for this product. | Enforce centrally: a mandatory scoped-query component (or Hibernate `@Filter` enabled per request) plus an ArchUnit/Modulith rule forbidding unscoped repository access from controllers. Run a time-boxed S1 spike on SQL Server Row-Level Security with `SESSION_CONTEXT` (reset per pooled connection) as defence in depth. |
| DR-03 | Major | ADR-006; RC-10; QA-04.8 | Hash-chain design is unspecified on three points that decide whether it works: (a) **concurrency**: a single global chain needs a serialised read of the previous hash (e.g. `UPDLOCK, HOLDLOCK` on a chain-head row) or concurrent writers fork the chain. That lock serialises all audited writes across all companies. (b) **atomicity**: the audit insert must be in the same transaction as the business change, or events can be lost or invented. (c) **canonical form**: field order, timestamp precision, decimal scale, null encoding and charset must be fixed, or verification breaks after a library upgrade. | Use one chain per company, with a chain-head row locked inside the business transaction. Specify a canonical serialisation (versioned, e.g. `v1`) in ADR-006. QA-04.8 then tests "no forks per chain". |
| DR-04 | Major | ADR-006; RC-10; spec §24 | As designed, the chain is only tamper-evident against people who cannot recompute it. A DBA or anyone with the app's DB credentials can rewrite rows *and* recompute every hash. "Application user has no UPDATE/DELETE" also conflicts with Flyway running as that same user. | (1) Separate DB principals: a migration owner (DDL) and a runtime user with INSERT/SELECT only on `audit_event`. Decide this in S1 even if dev uses one Windows login. (2) Periodically export the signed chain head (HMAC with a key held outside the DB, or written to WORM/external storage). Add both to the S9 hardening scope and state the remaining limits in sales material. |
| DR-05 | Major | roadmap S2 vs S4; mvp.md; ADR-005 | Approval thresholds are by amount (§7.1) and requests may be in a currency other than the company currency (§6.1 "devise"), but exchange rates arrive in S4. S2 circuits cannot evaluate "amount > X" consistently. | Move the currency and exchange-rate reference data (admin entry + rate on date) into S2. Define: the threshold is compared in **company currency**, converted at the rate on the submission date and stored on the request. |
| DR-06 | Major | roadmap S1-AC-03 vs spec §6.1 | S1-AC-03 puts a currency on each **line**. The spec has one estimated amount and currency per request (§6.1 "Budget"). Mixed-currency lines make the header total, thresholds and S1-AC-06 "amount and currency" undefined. | One currency per request in the MVP. Lines inherit it. Fix S1-AC-03. |
| DR-07 | Major | roadmap S1-AC-05; QA J1.3; spec §5 | S1 ends at "Submitted", but no circuit exists until S2, and that status name is not in the spec's lifecycle ("Brouillon → Demande créée → En validation"). QA J1.3 expects "En validation". The S1 demo state is ambiguous, and the status must be migrated in S2. | Use spec statuses with stable codes (`DRAFT`, `CREATED`, `IN_APPROVAL`, …) and EN/FR labels. In S1, submit moves `DRAFT → CREATED` and stops there, documented as such. Publish the full status enumeration (including per-line statuses, A2) in S1 so later sprints add transitions, not statuses. |
| DR-08 | Major | mvp.md; roadmap S7; spec §16.2, US-10 | The core promise "where is it / who is responsible, since when" lands in S7, but it depends on data every earlier sprint must record: current owner and `owner_since` on each transition, planned vs actual dates per stage. If S1–S6 don't capture these, S7 cannot reconstruct them. | Add `current_owner`, `owner_since` and a stage timeline to the request model in S1. Make each sprint's AC include "request detail shows current stage, owner, since when". S7 then only aggregates. |
| DR-09 | Major | mvp.md "Receipt & closure"; register FR-RCV-02/03; spec §13 | Closure conditions 2–3 (§13) require the final invoice document and amount. Invoice capture is not in the MVP (three-way match is P2), so the MVP closure rule cannot be satisfied and MVP acceptance criterion 7 is untestable. | Add a manual "final invoice: number, amount, currency, document" capture to S6 (no matching). Keep three-way match in P2. |
| DR-10 | Major | recommended-changes RC-05; register; spec §4 | Deferrals from the spec's Phase 1 are only partly recorded as proposed changes: M17 "Phase 1 (demande et suivi)" plus US-13/US-14/US-16; M6 payments/LC/guarantees (§11, Phase 1); M12 Phase 1 document reading; M9 administrative dossier with expiry alerts; M14 full-text/OCR search, versions and preview; §7.1 parallel/conditional circuits. Several appear only as "Deferred" in the register, without an RC entry or client confirmation. The "Négoce" model (§2) is entirely out of scope. | List every Phase 1 → Phase 2 move as an explicit RC row and get client sign-off before S1 planning. These are commercial decisions, not technical ones. |
| DR-11 | Major | ADR-005; spec §7.1 | §7.1 explicitly lists parallel and conditional circuits. A sequential-only rule table covers US-04 only partially. Parallel "all-of/any-of" step groups are cheap if designed in now, expensive to retrofit. | Model a circuit as ordered **stages**, each holding one or more approvers with an `ALL`/`ANY` policy and an optional condition (category, amount band, purchase type). Keep the BPMN designer deferred. |
| DR-12 | Major | roadmap S2/S3; architecture §2 | No notification channel is decided. Reminders, escalation (§7.1), information requests and approval "from the phone" (US-03) need e-mail at minimum. In-app only will not reach approvers. | Decision record: SMTP through the outbox from S2, with localised templates in the recipient's stored language and deep links. Push/PWA later. |
| DR-13 | Major | ADR-004; S0-AC-10 | Language preference lives only in `localStorage`. E-mails, exports, generated PDFs and server-side validation messages need the user's language on the server. | Persist `preferred_language` on `user_account` from S1. `localStorage` is then only a cache or the pre-login choice. Backend message bundles EN/FR for `ProblemDetail` details and e-mails. |
| DR-14 | Major | ADR-001; architecture §1 | Windows integrated auth via the `mssql-jdbc_auth` DLL is Windows-only. Spec §22 targets Docker/Kubernetes (Linux). The DLL version must also match the driver exactly. Risk: a dev default silently becomes the production assumption. | State in ADR-001 that integrated auth is dev-only. Production uses SQL auth from a secret store, Kerberos (`authenticationScheme=JavaKerberos`), or Entra ID. Non-dev profiles must fail fast when `DB_URL` is unset (no localhost default). |
| DR-15 | Major | S0-AC-06; architecture §5 | `/api/v1/system/status` exposes DB product version and schema version unauthenticated. Acceptable on a dev laptop, an information disclosure in any shared environment. | S1 AC: restrict version details to administrators. The public health response returns UP/DOWN only. Actuator `show-details` set to `when-authorized`. |
| DR-16 | Major | analysis A10; QA J1.10 | Money rules are incomplete. (a) Quantity type and precision are undefined (fractional units: m, kg, L). (b) FX rate precision and direction (`1 EUR = x TND` vs inverse) are undefined. (c) Currency minor units differ (TND 3, EUR 2, JPY 0); `DECIMAL(19,4)` stores them, but rounding of totals must follow the currency. (d) "Banker's rounding" is unusual for Tunisian/French accounting and ERPs (usually HALF_UP), so totals may disagree with the ERP export. | Decide and record: quantity `DECIMAL(19,4)` with unit of measure; rate `DECIMAL(19,8)` as "units of quote currency per 1 base currency" with date and source; ISO-4217 minor units in the currency table; round line totals to currency minor units, HALF_UP, configurable per company. Add these to an ADR before S1. |
| DR-17 | Minor | analysis A11; ADR-001 | "`DATETIMEOFFSET`/`DATETIME2` UTC" leaves the choice open. Hibernate maps `Instant` according to its preferred JDBC type, so a mismatch shifts times. Calendar fields (required date, ETA) are dates, not instants. | Pick one: `DATETIME2(3)` holding UTC ↔ `Instant` (set `hibernate.type.preferred_instant_jdbc_type` accordingly and test it), or `DATETIMEOFFSET` everywhere. Use `DATE` ↔ `LocalDate` for business dates. Per-company calendars for SLA (§3.6 "calendrier des jours ouvrés"). |
| DR-18 | Minor | ADR-001 | `IDENTITY` keys disable Hibernate batch inserts (lines, audit, imports). Request numbers "per company per year" cannot use SQL Server `SEQUENCE` objects practically. | `BIGINT` keys from `SEQUENCE` with a pooled optimizer for high-volume tables. Business numbers from a counter table (`company_id, year, kind → next_value`) incremented under `UPDLOCK` in the submit transaction. |
| DR-19 | Minor | ADR-001 | The UTF-8 collation brings nothing for `NVARCHAR`. Where server and database collations differ, temp-table joins raise collation conflicts. CI_AS treats "Société" and "Societe" as different for uniqueness of supplier names and codes. | Keep `NVARCHAR` throughout, document that. Use `COLLATE DATABASE_DEFAULT` in temp tables. Decide accent sensitivity for duplicate detection of suppliers and articles (an application-level normalised key is recommended). |
| DR-20 | Minor | ADR-001; spec-review C1 | Edition-dependent features are assumed without edition checks. Full-text search needs Express *with Advanced Services* or higher. Express is capped at 10 GB per DB, 1 socket/4 cores and about 1.4 GB buffer pool. TDE is available in Standard only from 2019. | Add a supported-editions matrix (minimum SQL Server 2019 Standard, Express for under 50 users with listed limits) to ADR-001 and the sizing guide. |
| DR-21 | Major | architecture §2 "Concurrency" | Optimistic locking plus conditional transitions cover two users acting at once, but not retries: phone double-taps, network retries, and re-sent ERP exports (§21.5 asks for idempotency keys). | `Idempotency-Key` header on state-changing POSTs from S2 (stored with the result for 24 h). The export batch ID is the idempotency key for ERP files (QA J5.5). |
| DR-22 | Minor | roadmap S1-AC-07 vs test-strategy "Permissions" | S1 says cross-company access returns 404, the test strategy says "every other role gets 403". Both are right for different cases but not stated, so QA and Dev will disagree. | Rule: a resource outside the user's scope → 404. In scope but action not permitted for the role → 403. Write it in architecture §5. |
| DR-23 | Minor | roadmap S1-AC-01/02 | Not testable as written. "Sessions/tokens expire" has no duration. "Roles and scopes from §20 are seeded" covers 12 roles with no list of demo users. | Specify idle and absolute timeout values (e.g. 30 min / 8 h), and a seeded demo-user table (user, company, roles, scope) in the S1 AC. |
| DR-24 | Minor | architecture §2; ADR-002 | Fifteen modules are listed up front. Creating empty modules or packages ahead of code adds noise, and `approval`/`request` boundaries may move once the state machine exists. | Create modules only when they get code. Revisit the request/approval split at the end of S2. |
| DR-25 | Minor | roadmap S8; mvp.md AC 12 | The AI quality gate is deferred to S8, and the labelled evaluation set does not exist. On-prem hardware/provider and data-residency are unknown and are commercial decisions. | Define the metrics now (e.g. per-field exact match for quantity/unit ≥ 95%, item description accepted without edit ≥ 80%, zero auto-submissions). Start collecting anonymised free-text samples (FR/EN) from S1 demos. Settle the provider and hardware assumption by S6. |
| DR-26 | Minor | architecture §6; NFR-09 | WCAG 2.2 AA is claimed but no automated accessibility check is in the quality gates. | Add axe-core checks to frontend tests or a Playwright smoke test from S1. Manual keyboard/screen-reader pass in each sprint's QA. |
| DR-27 | Minor | NFR-07; backlog #10 | CI is planned, but no platform or repository host is chosen (no git remote). | Decision in S1: GitHub Actions / GitLab CI / Azure DevOps. Without Docker, the runner needs SQL Server (Windows runner, or a service container on Linux CI). |
| DR-28 | Minor | mvp.md; spec §21.5 | US-12 export is in S7, but ERP mapping tables (§21.5: companies, suppliers, articles, accounts, currencies) and `erp_reference` columns should exist on the aggregates as they are created. | Add `erp_code` columns and a generic `erp_mapping` table when each aggregate is introduced (companies S0/S1, suppliers S4, articles S4, POs S5). |
| DR-29 | Minor | test-strategy "Test data" | "Each test inside a transaction rolled back" is incompatible with concurrency tests (QA-04.8, J1.4) and with chain-head locking. | Allow committed-data tests with unique company codes plus cleanup for concurrency and audit scenarios. |
| DR-30 | Suggestion | decision-log; spec §22 | Spec says Spring Boot 3. The project uses Boot 4.1 (the 3.x line's OSS support has ended), but no decision records the change. | Add ADR-008 "Spring Boot 4.1 / Java 21" with the support-window rationale. |
| DR-31 | Suggestion | roadmap; mvp.md | The 20-week plan has no stated team capacity, so it cannot be validated. S6 (logistics + receipt + photos + closure + invoice capture per DR-09) is the most overloaded sprint. | State the assumed team size. Consider splitting S6, or moving logistics milestones to S5 alongside the PO. |

## Open business rules raised by QA — recommended defaults

| QA ref | Question | Recommended default | Rationale |
|---|---|---|---|
| J1.1 | Do drafts get a (provisional) number? | **No.** Drafts show "Draft" plus an internal ID. The official `{COMPANY}-PR-{YYYY}-{seq6}` is assigned at submission. | Abandoned drafts don't consume numbers. The spec lifecycle distinguishes "Brouillon" from "Demande créée". Users only quote numbers of submitted requests. |
| J5.3 | PO amount vs approved amount | A PO may exceed the approved estimate (in company currency) by up to **10% or a per-company absolute cap, whichever is lower**, with a mandatory reason. Above that, a management re-approval step is required. Decreases are always allowed. Tolerances are configurable per company. | Common delegation-of-authority practice. Prevents bypassing approval thresholds, a fractioning-like risk (§18). |
| J6.4 | Over-receipt | **Blocked by default (0%).** An optional per-category tolerance (e.g. 5% for bulk materials) can be configured. Anything beyond requires a PO amendment by the buyer. | Protects three-way match and budgets. Bulk goods legitimately vary. |

## Summary

Before S1 starts: DR-01 (multi-company visibility model). Before S1 is planned: DR-03/04 (audit chain concurrency and
real tamper evidence), DR-05/06 (currency of thresholds and requests), DR-07/08 (status codes and owner tracking from
day one), DR-09/10 (closure needs invoice capture; client sign-off on Phase 1 deferrals), DR-14/15/16 (production DB
auth, status endpoint exposure, money rules).
