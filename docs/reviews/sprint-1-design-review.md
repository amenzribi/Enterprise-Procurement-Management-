# Sprint 1 Design Review

Reviewer: independent design review before implementation. Scope: `docs/product/sprint-1.md` against the
specification (§3.2, §5, §6, §7.2, §20, §24), ADR-005/006/007, `docs/analysis/design-review-response.md`,
`CLAUDE.md`, and the Sprint 0 code (V1–V3, `AuditLog`, FrontEnd `app.config.ts`, `language.service.ts`).
Static review, nothing built or run.

Severity: **Blocker** = must change before implementation; **Major** = must be in the Sprint 1 implementation or
explicitly re-scoped by the lead; **Minor** = fix in sprint if cheap, otherwise record; **Suggestion** = optional.

No Blocker. Eleven Major findings, mostly about security mechanics that are easy to get subtly wrong with
Spring Security 7 + an Angular SPA, and two data-model gaps that are expensive to add later.

## Findings

| ID | Severity | Reference | Finding | Recommended action |
|---|---|---|---|---|
| S1DR-01 | Major | sprint-1 Technical design "CSRF"; API `GET /auth/csrf` | Since Spring Security 6, the default CSRF request handler (`XorCsrfTokenRequestAttributeHandler`, BREACH protection) expects a *masked* token. An SPA echoing the raw `XSRF-TOKEN` cookie in `X-XSRF-TOKEN` is rejected with 403. The token is also *deferred*: the cookie is not written until something reads the token, so the `GET /auth/csrf` endpoint must explicitly load it. After sign-in (`CsrfAuthenticationStrategy`) and sign-out the token is replaced or cleared. | Use Spring Security's SPA configuration (`csrf.spa()` in Spring Security 7, or the documented `SpaCsrfTokenRequestHandler`) with `CookieCsrfTokenRepository.withHttpOnlyFalse()`. In `GET /auth/csrf`, read `CsrfToken.getToken()` to force the cookie. Frontend: call it on app start and again after sign-out, before the next sign-in. Angular's built-in XSRF support (enabled by default with `provideHttpClient`, works with `withFetch`) only adds the header to relative, non-GET URLs, so keep API calls relative. Test: a POST without or with a stale header returns 403 `csrf-invalid`; the frontend re-fetches once and retries. |
| S1DR-02 | Major | sprint-1 AC-01 "session id rotated at sign-in"; `POST /auth/login` | A JSON login *controller* does not get the protections that `formLogin()` applies automatically. Spring Security 6+ requires an explicit `SecurityContextRepository.saveContext(...)`. Session-fixation protection (`changeSessionId`) and CSRF token rotation are `SessionAuthenticationStrategy` calls that only the filter chain makes. A hand-written controller that calls `AuthenticationManager` and sets `SecurityContextHolder` will either not persist the login or keep the pre-login session id. | In the login controller: authenticate, call `sessionAuthenticationStrategy.onAuthentication(...)` (a composite of `ChangeSessionIdAuthenticationStrategy` and `CsrfAuthenticationStrategy`), create an empty context, set it, and call `securityContextRepository.saveContext(...)`. Alternatively, configure a JSON `AbstractAuthenticationProcessingFilter`. Tests: the session cookie value changes after sign-in; the old session id is rejected; `GET /me` succeeds in a new request. |
| S1DR-03 | Major | sprint-1 AC-01 lockout; API `423 account-locked` | (a) **Enumeration:** returning 423 only for existing accounts reveals which e-mails exist, and which are locked. Timing does too: no bcrypt runs when the e-mail is unknown. (b) **Denial of service:** five failed tries lock any known account for 15 minutes; `ceo@` and `admin@` can be locked out at will. | Return the same 401 `invalid-credentials` body for unknown e-mail, wrong password and locked account. Run a dummy bcrypt check when the user is unknown. Replace the hard lock with throttling per account and per client address: increasing delays after five failures and a temporary block, logged, with an admin unlock in S1 or S2. Never reveal the lock state before the password is verified; after a correct password on a locked account, a distinct `account-locked` message is acceptable. Update the counter atomically (`UPDATE … SET failed_attempts = failed_attempts + 1`). |
| S1DR-04 | Major | sprint-1 Technical design "Audit" (sign-in failures in the global chain); ADR-006 | Every failed sign-in would take the `global` chain-head lock (`UPDLOCK, HOLDLOCK`, held until commit) and append an immutable row. A credential-stuffing burst then serialises on one lock and permanently writes attacker-supplied strings (any e-mail text) into a tamper-evident store that cannot be purged (privacy law, spec §24 "données personnelles"). | Record successful sign-ins, sign-outs and lockouts in the audit chain with the user id. Send failed attempts for unknown accounts to the application log or a non-chained `security_event` table without the raw identifier (truncated or keyed hash of the e-mail, client address), with retention. If failures stay in the chain, rate-limit before auditing. |
| S1DR-05 | Major | sprint-1 AC-02 "demo users exist only when the demo profile is active"; Sprint 0 QA-D-02 (`repeatable:missing`) | Contradiction. Since QA-D-02, demo rows stay in the database when the app is later started without `demo`. Demo users created by a demo-only initialiser would therefore stay able to sign in under any profile, including a non-demo deployment that reuses the database. The initialiser also needs a guard against running on a real database. | Add `is_demo BIT` to `user_account`, or mark demo credentials. At startup, when `demo` is **not** active, refuse authentication for demo accounts (or deactivate them), and test it. The demo initialiser refuses to run when non-demo companies exist and logs a warning banner. With a random password: set it only when creating users, or reset all demo passwords at each demo start, and say which in the README (QA needs a stable `DEMO_USER_PASSWORD`). Print the generated password once, as a single console line, at WARN level. |
| S1DR-06 | Major | sprint-1 AC-08 optimistic locking; Technical design "Request model" | Two JPA pitfalls defeat AC-08. (1) The client's `version` must be compared **explicitly** with the loaded entity's version. Hibernate checks the version it loaded milliseconds earlier, not the one the user saw, so a stale browser tab silently overwrites newer data. (2) Changing only lines (`purchase_request_line`) does not increase the parent's `@Version`, so the requester and the assistant (both may edit the same draft, AC-04 and visibility table) can each change lines without conflict. | In update and submit: if `dto.version != entity.version`, return 409 `stale-version` before applying changes. Lock the aggregate with `LockModeType.OPTIMISTIC_FORCE_INCREMENT`, or always modify the header (`updated_at`, `updated_by`) on any line change. Return the new version in every response. Tests: a stale version is rejected; two concurrent line-only edits produce one 409. |
| S1DR-07 | Major | sprint-1 AC-04 actor rules; DR-01 visibility model; spec §3.2, §3.7, US-15 | The requester chooses the **buying company** (self or purchasing centre) and the **charged company** (any company in the group). Under the visibility model (design-review-response), `buying_company_id` and `charged_company_id` grant visibility to purchasing and finance of *those* companies. So a client-controlled field decides which other company sees the request and whose budget pays. The spec gives the purchase-mode decision to the purchasing centre at assignment (§3.7 "la centrale peut le modifier au moment de l'affectation", US-15, Sprint 3) and says the charged company is "en général la société demandeuse". | Sprint 1: derive both server-side. Charged company = requesting company (changeable only with an explicit permission later). Buying company = default from the company's `purchasing_mode` (DIRECT → self; CENTRALIZED → the group's PURCHASING_CENTER; MIXED → self until category rules exist), stored as *proposed*. The requester may view them but not change them. The fields still exist, satisfying "recorded separately". Tests: the body cannot override them (422). |
| S1DR-08 | Major | sprint-1 status model; spec §5; assumption A2 | (1) The header and line enumerations are disjoint after ordering. The header has `IN_TRANSIT`, which isn't in the spec, and lacks `IN_PRODUCTION`, `READY`, `SHIPPED`, `AT_PORT`, `IN_CUSTOMS`, `IN_WAREHOUSE`, `NON_CONFORMING`, which exist only on lines. So the A2 rule ("header = least advanced active line status") cannot be computed. (2) The line enumeration lacks invoicing and closure states and any pre-order state (lines sit at `OPEN` through approval, sourcing and evaluation). (3) §7.2 "Demander une information" suspends the deadline but has no state or flag. | Publish one **ordered** progression for the execution phase, shared by header and lines: `ORDERED, CONTRACT_SIGNED (header only), ORDER_CONFIRMED, IN_PRODUCTION, READY, SHIPPED, AT_PORT, IN_CUSTOMS, IN_WAREHOUSE, DELIVERED, PARTIALLY_RECEIVED, NON_CONFORMING, RECEIVED/ACCEPTED, INVOICED, PAYMENT_PENDING, PAID, CLOSED`. Header-only states cover before the order (`DRAFT…MANAGEMENT_VALIDATION`) and `REJECTED`, `CANCELLED`. Drop `IN_TRANSIT`, or map it as the local-purchase equivalent of `SHIPPED` (§12.1 "En transit local") and say so. Model "information requested" as a flag or sub-state of `IN_APPROVAL` (`awaiting_requester_info`), not a status. Keep codes stable; label in EN/FR. |
| S1DR-09 | Major | sprint-1 AC-11; DR-08 ("stage timeline from S1"); design-review-response DR-08 | The design stores only `current_owner_user_id` and `owner_since` on the request. DR-08 asked for a **stage timeline** from S1 so S7 (US-10 "écart entre dates prévues et réelles, par étape") can aggregate rather than reconstruct. Rebuilding it from the hash-chained audit payload is possible but fragile and slow, and every sprint would depend on audit payload format. | Add `purchase_request_transition (id, request_id, from_status, to_status, owner_user_id, owner_since, actor_user_id, occurred_at, planned_due_at NULL)`, written in the same transaction as the status change and the audit event. Request detail renders the timeline from it. Cheap now, a data migration later. |
| S1DR-10 | Major | sprint-1 Technical design "Numbering" + "Audit"; `AuditLog.record` | A submit holds three exclusive locks until commit: the `document_counter` row, the company's `audit_chain_head` (both acquired immediately through JDBC), and the request row. The request row lock is taken whenever Hibernate flushes, normally at **commit**, after the JDBC locks, but earlier if any JPQL/native query triggers auto-flush. Lock order therefore depends on incidental code and can differ between submit, draft save and later sprints' approval actions, a classic SQL Server deadlock (error 1205) source. First insert of a counter row (new company/year): `UPDLOCK, HOLDLOCK` on a missing key takes key-range locks; two first submissions can still deadlock on the subsequent INSERT. | Define and document one lock order: **request row → document_counter → audit_chain_head**. Load the request with a pessimistic or force-increment lock, or `flush()` the request first, then the counter, then audit. Create counter rows race-safely: `INSERT … SELECT … WHERE NOT EXISTS` under `UPDLOCK, HOLDLOCK`, or pre-create the row for (company, year) at the first draft save or company creation. Add bounded retry on deadlock (1205) around submit and test it: ≥ 20 parallel submissions in one company **including the first-of-year row**, no gaps, no duplicates. |
| S1DR-11 | Major | sprint-1 AC-15 (unsaved changes), AC-01 (30-min idle); spec "expired-session state" | A requester filling a long multi-line form for more than 30 minutes without a server call (editing generates no requests) is signed out. The next save returns 401, and the planned interceptor redirects to sign-in, **losing the unsaved form**. This directly contradicts AC-15. Separately, if the frontend polls `GET /me` to show `sessionExpiresAt`, each poll resets the idle timer, so the idle timeout never applies. | Warn about two minutes before idle expiry ("Stay signed in" pings once on a user gesture). On 401 `session-expired` during save, keep the form state in `sessionStorage` (per user, not after sign-out), sign the user back in in place (modal or return URL), and restore the form. Compute the expiry client-side from `idleTimeoutSeconds` and the last request time; no background polling. Test: an expired session during save keeps the entered lines after re-sign-in. |
| S1DR-12 | Minor | sprint-1 Technical design "Session" (absolute 8 h by session creation time) | `changeSessionId()` keeps the same session object, so `getCreationTime()` predates sign-in when a session existed before login (e.g. a saved request), which shortens the 8 h window. | Store `authenticatedAt` as a session attribute at sign-in and compare with it. Return `401 session-expired` from the filter and invalidate the session. Expose `sessionExpiresAt = min(lastAccess + 30 min, authenticatedAt + 8 h)`. |
| S1DR-13 | Minor | sprint-1 Technical design "API auth errors" | Distinguishing `session-expired` from `unauthenticated` needs `request.getRequestedSessionId() != null && !request.isRequestedSessionIdValid()`. After a server restart (in-memory sessions), every signed-in user sees "session expired", which is acceptable but should be documented. Leaving the default entry point redirects to `/login`, and `httpBasic()` triggers the browser's authentication pop-up. | Custom `AuthenticationEntryPoint` and `AccessDeniedHandler` writing `ProblemDetail` (`unauthenticated`, `session-expired`, `forbidden`, `csrf-invalid`). Disable `formLogin`, `httpBasic` and the request cache. Document that a restart signs everyone out (single-node, ADR-003). |
| S1DR-14 | Minor | sprint-1 roles; `user_role(user_id, role, company_id NULL)`; spec §20 | (a) `DEPARTMENT_MANAGER` scope is a department, but `user_role` has no `department_id`, so someone managing two departments cannot be modelled. (b) `company_id NULL` = "all group companies" is safe for GROUP_MANAGEMENT/ADMIN but dangerous if set for REQUESTER etc. (c) §20 roles not yet listed (budget/management approver, technical validator, logistics, finance, sales, external customer, and the **auditor** of US-11) will arrive later. A `CHECK` constraint listing roles would force a migration each time. | Add `department_id NULL` (same-company FK) to `user_role`. Add a CHECK that allows `company_id IS NULL` only for GROUP_MANAGEMENT, ADMIN (later AUDITOR). Keep roles as validated strings in code, without a DB CHECK list, or a `role` reference table. Add a note listing the §20 roles and their target sprints. |
| S1DR-15 | Minor | sprint-1 visibility table; AC-04 | Ambiguities: (1) Which companies can a user choose as **requesting company**: only their own, or any company where they hold `ENTER_ON_BEHALF`? (2) Who may **submit** a draft entered on behalf? The table implies both requester and assistant, but §3.2 makes the requester responsible. (3) `entered_by` should be the creator and never change on later edits; the last modifier needs its own column. | (1) Requesting company = the user's own company in S1. Cross-company entry on behalf only when the role assignment's `company_id` grants it. (2) Both may submit; the audit records who did. State it in the AC. (3) `entered_by_user_id` is immutable; add `updated_by_user_id`. |
| S1DR-16 | Minor | sprint-1 AC-03 vs spec §6.1 | Missing §6.1 fields that are cheap now and costly to migrate later: **origine** (internal/external; keep the column even though RC-15 is unapproved, per the client's "keep requirements" instruction), **ligne budgétaire** (C7: MVP stores the budget line as a reference), urgency justification (**"urgence motivée"**, required when priority = URGENT), link to **equipment / maintenance order** reference. Country is derived from the company. | Add `origin` (default INTERNAL), `budget_line_ref NULL`, `urgency_justification NULL` (required at submit when URGENT), `equipment_ref NULL`, `maintenance_order_ref NULL`. Translate the labels. |
| S1DR-17 | Minor | sprint-1 AC-03/05 | Validation rules incomplete: (a) required date must be ≥ today **in the company time zone** at submission (same check for line dates if present); (b) the request number year `YYYY` must be taken in the company time zone (31 Dec 23:30 UTC is already 1 Jan in Tunis); (c) rounding order: compute line total = round(qty × price, minor units), request total = sum of rounded line totals, and say so; (d) unit of measure is free text, which blocks later ERP mapping (§21.5). | Add (a)–(c) to the AC with tests. For (d), use a seeded unit list (UN/CEFACT subset: EA, PCE, KG, M, L, SET, H…) with EN/FR labels, or at least normalise to upper-case codes. |
| S1DR-18 | Minor | sprint-1 API contract | Gaps the UI will need: (1) **allowed actions** on detail/list (`actions: ["EDIT","SUBMIT","DISCARD"]`) so the UI doesn't re-implement permissions; (2) **discard draft** (`DELETE /requests/{id}`, DRAFT only, audited), otherwise junk drafts accumulate; (3) `mine=true` vs other scopes is undefined for managers and CEO: use `scope=mine\|visible`; (4) **sort allow-list** and max page size are unspecified; Spring Data `Sort` from raw input allows sorting on any property, including nested or unexpected ones; (5) field-error format for lines (`lines[2].quantity`) and **parameters** (`{code:"max-decimals", params:{max:4}}`) so messages can be specific; (6) a stable error code for `status-transition-invalid` versus `stale-version`. | Add these to the contract. Sort allow-list: `number, title, status, totalAmount, requiredDate, updatedAt` (default `updatedAt,desc`); `size` ≤ 100. Unknown sort or filter → 400 `invalid-parameter`. |
| S1DR-19 | Minor | sprint-1 AC-14 | "Controller must not depend on a repository" does not stop a **service** from calling `PurchaseRequestRepository.findById` unscoped, the actual leak path (DR-02). Spring Modulith cannot express class-level rules; ArchUnit would be a new test dependency. | Make the request repository package-private, with only `RequestAccessPolicy` / scoped query class allowed to use it. ArchUnit (test scope, Apache-2.0) rule: no class outside the scoped-query component accesses `PurchaseRequestRepository`, and no controller accesses any `Repository`. Keep `findVisible(id)` the only lookup. |
| S1DR-20 | Minor | sprint-1 Technical design "Audit"; `AuditLog.record` | Auditing every **draft save** in the company chain serialises all draft saves of a company on the chain-head lock and adds rows of low audit value. `AuditLog` uses its own `JdbcTemplate` and relies on `JpaTransactionManager` exposing the JDBC connection (HibernateJpaDialect does, so atomicity holds). But this is untested with JPA entities in the same transaction. | Audit: draft created, submitted, discarded. Record draft edits as a single `updated` event per save, or not chained (decide and document). Add a test that an exception after `auditLog.record` (e.g. a forced failure at flush) rolls back both the request and the audit row, using JPA entities, not only JDBC. |
| S1DR-21 | Minor | sprint-1 AC-12; `language.service.ts` (localStorage) | Precedence is undefined when a user changes language on the sign-in page and their account says otherwise. Switching language while signed in must also persist to the account, and a failure must not revert the UI. | Rule: at sign-in the account preference wins, unless the user changed language on the sign-in page itself in this visit; then save that choice to the account. Signed-in switches call `PUT /me/preferences` (fire-and-forget, with a non-blocking error toast). localStorage stays the pre-login cache. |
| S1DR-22 | Minor | sprint-1 AC-13; `application.yml` (`show-components: always`) | Anonymous `/actuator/health` must return only the top-level status, but `show-components: always` lists component names (CR-06). `GET /api/v1/system/status` "requires sign-in": the System status page is currently public, so the frontend route also needs the auth guard. The page must still work in DOWN conditions after sign-in. | `show-components: when-authorized`, `show-details: when-authorized`, `roles: ADMIN`. Guard the route. Test anonymous, requester and admin views. |
| S1DR-23 | Minor | V1 `document_counter` comment vs assumption A1 | V1 comments "Gap-free business numbers", while A1 says "gap-free not guaranteed". With the counter incremented inside the submit transaction, rollback reverts the increment, so numbers *are* gap-free unless a committed request is later deleted. `seq6` overflow beyond 999 999 per company per year is undefined. | Align A1 with the implementation ("gap-free per company and year; submitted requests are never deleted, only cancelled"). Define overflow: widen to 7 digits, without truncation. |
| S1DR-24 | Suggestion | sprint-1 AC-03 "1..100 lines" | Spare-parts lists (§6.2 Excel import, S7) commonly exceed 100 lines. | Make the limit configurable (default 200), enforced server-side, and check with the client. |
| S1DR-25 | Suggestion | sprint-1 AC-16, Technical design "Frontend" (Playwright with installed Edge/Chrome channel) | Using the system browser channel avoids a browser download but makes results depend on the local browser version, and CI (DR-27, platform undecided) will need a bundled browser anyway. | Configure `channel: 'msedge'` locally with fallback to the bundled Chromium (`npx playwright install chromium`), and record which was used in QA evidence. |
| S1DR-26 | Suggestion | Over-engineering check | The scope is large but not gold-plated. The full status enumeration with EN/FR labels (~40 codes) is justified by DR-07 and avoids later renames. Two items could be trimmed if the sprint runs late without harming the objective: `GET /requests/statuses` (statuses can be a shared constant compiled into the frontend from the same list, with a test that both agree), and per-line delivery location (header-level is enough for the S1 journey). Do **not** trim the security, isolation, numbering or audit items. | Keep as fallback descoping options; decide at mid-sprint. |

## Checks of the design against the spec (no finding)

- Visibility table vs §20: requester (own, A4), department manager (department, non-draft), group management (all companies, non-draft), with buyer/purchasing roles deferred to S3, are consistent with §20 and DR-01 once S1DR-07 is applied. ADMIN without business data access is a sound reading of §20 "Voit : Configuration".
- 404 for out-of-scope on list, detail, update and submit matches ADR-007 / DR-22.
- In-memory `HttpSession` for a single node is proportionate (ADR-003); Spring Session JDBC is correctly deferred.
- `user_credential` separate from `user_account` keeps production OIDC users password-less, as intended.
- Audit inside the caller's transaction (`AuditLog.record` is `@Transactional` REQUIRED and uses the transaction-bound connection) satisfies "persist submission and audit atomically", subject to the test in S1DR-20.
- Cookie path / `SameSite=Lax`: the dev proxy makes frontend and API same-origin (`localhost:4200`), so cookies need no domain attribute. `Secure` cookies are accepted by Chromium-based browsers on `http://localhost`, so `Secure` can stay on in `demo` too.
