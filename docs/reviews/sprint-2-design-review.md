# Sprint 2 Design Review

Reviewer: Reviewer agent · Date: 2026-10-27 · Scope: `docs/product/sprint-2.md` against Solution Guide v3.0 (Steps 0–2,
§7, §8, §9, §12), `docs/analysis/solution-guide-v3-review.md`, French spec v2.1 §7, and the Sprint 1 code (`request`
module, `RequestAccessPolicy`, `RequestStatus`, `TransactionLocks`, audit, `identity.Role`, migrations V1–V4).
Static review only; nothing built or run.

**Verdict:** the design is sound and traceable to v3.0, with no blockers. Thirteen Major findings must be settled
before or at the start of implementation. Most of them are rules the design leaves undefined: stuck S1 requests,
self-approval, revision editing, rule overlap, one-tap token handling, outbox and SLA semantics, and attachment
hardening. The sprint is large. S2DR-16 proposes an order of cuts.

| ID | Severity | Reference | Finding | Recommended action |
|---|---|---|---|---|
| S2DR-01 | Major | S2-AC-04; `RequestStatus.CREATED` | Requests submitted in Sprint 1 are `CREATED` with no circuit (procurement_dev already holds several, and S1 numbering has issued numbers). After S2 they show "Submitted" forever with no next actor, which contradicts v3.0 "one owner at each step". | Add an idempotent start-up/backfill job (or admin action) that starts a round for each `CREATED` request, using the rule and rate at its `submitted_at`. Requests with no rule or rate stay `CREATED` and appear in an admin "awaiting approval circuit" list. QA scenario: an S1 request moves into an inbox. |
| S2DR-02 | Major | S2-AC-02/05; spec v2.1 §7.1 (DoA matrix); v3.0 §12 integrity | **Self-approval.** Karim (department manager) can submit a request for himself, or Leila can be both requester and budget approver. Nothing prevents a user approving their own request, or the entered-by assistant approving the request they typed. | Exclude the requester and entered-by user from every task. If a stage then has no approver, route to the stage's escalation role (or the next stage) and record "skipped: segregation of duties". Test it. |
| S2DR-03 | Major | S2-AC-02 stage types | **Unresolvable stage.** `DEPARTMENT_MANAGER` with no manager for the request's department, or no `BUDGET_APPROVER` in the company: the requester gets an error they cannot fix. | At submit, resolve all stage approvers up front. An empty stage falls back to the escalation role. If that is empty too, return 422 `no-approver-available` and notify company admins. Rule activation should warn about stages that resolve to nobody in the company today. |
| S2DR-04 | Major | S2-AC-05 return; `RequestAccessPolicy.canEdit` | "Return for revision → requester edits and resubmits", but `canEdit` allows only `DRAFT`. Resubmission is undefined: renumbering, rule and rate re-evaluation, and what happens to old tasks and links. The doc also says both "requests keep the version they started with" and "circuit restarts from stage 1". | Allow edit, attachments and resubmit in `REVISION_REQUESTED` for editors. Keep the number; do not call `RequestNumbering`. Each **round** snapshots the rule version, rate and converted amount at round start (resubmission = new round, re-matched). Previous-round tasks are cancelled and their link tokens invalidated. Transition `REVISION_REQUESTED → IN_APPROVAL` is audited. |
| S2DR-05 | Major | S2-AC-02 "most specific wins; ties are a config error" | Detecting ties at submit time makes the requester pay for an admin mistake. Band boundaries are undefined: the demo uses "4 999.999", which breaks for EUR (2 decimals). The specificity order is unstated. | Validate at **activation**: within one company, rules of equal specificity must not have overlapping bands. Bands are half-open `[min, max)` in company currency, `max` NULL meaning unbounded. Specificity: category+type > category > type > none. Submit-time ambiguity cannot happen; keep `ambiguous-approval-rule` only as a defensive 500-class log, not a user error. Rule versions are immutable once activated. |
| S2DR-06 | Major | S2-AC-03 | The rate direction is ambiguous ("quote currency per 1 base currency" without saying which is the base when converting request→company currency). No inverse lookup, rounding or date semantics are given, and rates can be edited in place under requests that reference them. | Store explicit pairs; look up `request currency → company currency`, else invert the opposite pair (`1/rate`, DECIMAL(19,8), HALF_UP). Converted amount HALF_UP to the company currency's minor units. Same currency means rate 1 with no lookup (and no `missing-exchange-rate`). Rate date = submission date in the requesting company's time zone. Rate rows are immutable (correction = new row with a later `created_at`, same date; latest wins). |
| S2DR-07 | Major | S2-AC-07 one-tap | The token sits in the URL **path** (`/a/:token`), so it lands in reverse-proxy/access logs, browser history, and the `Referer` of any outbound request. The CSRF bootstrap for an unauthenticated POST is unstated. The token stays valid if the approver is deactivated, loses the role, or the task is delegated. Anyone the e-mail is forwarded to can see the summary. | (1) Put the token in the URL **fragment** (`/a#t=…`): never sent to the server or in Referer. The SPA reads it, calls `history.replaceState` to drop it, and sends it in the POST body/GET header. (2) `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on the page and API. (3) CSRF: the page calls `/auth/csrf` first, so the same double-submit applies. (4) At POST, re-check: user active, still holds the role or delegation, task `PENDING` and still assigned to that user, round current; otherwise show the neutral page. (5) Log only the token hash prefix. (6) Keep the summary minimal (no attachments, no line prices beyond the total). Document the forwarding risk. (7) Rate-limit GET and POST per IP and per token (reuse `LoginThrottle` pattern). |
| S2DR-08 | Major | S2-AC-05/08; lock order | **Races.** A link approve and an inbox reject (or two ALL approvers, or reminder escalation) on the same request. The link path must not be a separate code path. The stated lock order omits the numbering counter and the outbox, and the audit chain head must stay last (Sprint 1 rule). | One `ApprovalService.decide()` used by inbox and link. Order: request row → document counter (first submit only) → round → tasks → outbox/in-app inserts → audit chain head last. Task decision = conditional update `WHERE status='PENDING' AND version=?`; the loser gets 409 `task-not-pending`. The DB test runs link-approve and inbox-reject in parallel: exactly one wins, and the chain is valid. |
| S2DR-09 | Major | S2-AC-05 question; S2-AC-09 SLA | The question semantics are incomplete. In an `ANY` stage, may another approver approve while a question is open? What if the requester answers after the task was cancelled or the round restarted? Working hours are fixed to Mon–Fri 08–17, but the weekend differs across the group's region, and "company time zone" doesn't say which company (requesting vs approver's). | Question belongs to the task. Other `ANY` approvers may still decide; that closes the stage and auto-closes the question (requester notified: "no longer needed"). An answer to a non-open question → 409. SLA uses the **requesting company's** time zone and a per-company work week (default Mon–Fri, configurable column now, holidays later). Store `due_at` on the task; on pause/resume store `paused_ms` and recompute `due_at`. |
| S2DR-10 | Major | S2-AC-09/10 outbox | "No duplicates" is not achievable with SMTP after a crash between send and mark. Multi-instance claiming and the language snapshot are unspecified. Reminders could fire twice if the flag is not set in the same transaction as the outbox insert. | State **at-least-once** with a stable `Message-ID` per outbox row (receivers dedupe). Claim rows with `UPDLOCK, READPAST` in a short transaction; status `PENDING → SENDING → SENT/FAILED`, back-off, `max_attempts`, dead-letter visible to admin. Render the template at enqueue time in the recipient's language at that moment. Reminder/escalation: set `reminded_at` / `escalated_at` on the task in the same transaction as the outbox insert, with a conditional update so one scheduler wins. |
| S2DR-11 | Major | S2-AC-12 attachments | Hardening is needed beyond "sniffed type". The risks are SVG/HTML stored XSS on inline download, filename header injection, macro-enabled Office files, unbounded totals, deletion audit, and the scanner state. | Allowed set by magic-number check (PDF, PNG, JPEG, WEBP, DOCX/XLSX/PPTX (zip + content-types), CSV/TXT). No SVG/HTML, and no `.docm/.xlsm`. Storage name = UUID under `app.storage.path` (never user input). Download: `Content-Disposition: attachment` (inline only for PDF/images), RFC 5987 filename, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`. Limits: 20 MB per file, 25 files / 200 MB per request; `spring.servlet.multipart` limits aligned. Scanner port sets `PENDING_SCAN/CLEAN/INFECTED`; download only when `CLEAN` (dev no-op marks CLEAN). Upload, new version and delete are audited; delete is soft. Authorisation via `ScopedRequests` on the parent request. |
| S2DR-12 | Major | S2-AC-13 visibility; ADR-007 | Task-based visibility is right, but a **named-user stage** can point to any user. Without validation, a rule could name a user of another group, granting them visibility. Delegates also gain visibility through tasks, so an ineligible delegate leaks data. The inbox and approval tables must go through the same scoped-query discipline as requests. | Rule editor: named user must belong to the same group and be active; delegate eligibility checked server-side (same company role, or admin-allowed, same group). Visibility predicate: `EXISTS (task for user on request)` added to `RequestAccessPolicy`; inbox queries joined to it. Extend the S1CR-08 architecture test to the approval tables. Cross-group tests for named-user and delegate. |
| S2DR-13 | Major | S2-AC-01 Arabic | `ck_user_account_language` **and** `ck_company_language` (V1) allow only `en, fr`. Bidi is unaddressed: request numbers, codes, e-mails and amounts inside RTL text reorder visually. E-mail clients don't load web fonts. Arabic wording produced without native review is a commercial risk that QA cannot test. | Migration extends both checks to `ar`. Wrap numbers, codes, amounts, e-mails and user-entered Latin text in `<bdi>` or `dir="ltr"` / `unicode-bidi: isolate`. Mirror directional icons only. Keep native date inputs (they follow `dir`). Confirm `ar-TN` CLDR data uses the `latn` numbering system (Maghreb locales do); add a unit test asserting Latin digits. E-mails: `<html lang="ar" dir="rtl">`, inline CSS, system Arabic font stack, request number wrapped in LRI/PDI in subjects. Record "Arabic texts pending native-speaker review" as an open item, not a passed check. |
| S2DR-14 | Minor | S2 technical design, statuses | The `userStatus` mapping is not written down: CANCELLED has no v3.0 status, and several internal codes map to one user status. Adding `AWARDED` needs the header **and** line CHECK constraints changed (V4). | Publish the mapping table in the code and docs, with a unit test covering every enum value. REVISION_REQUESTED→RETURNED; IN_APPROVAL/CREATED→SUBMITTED; APPROVED/IN_PURCHASING_REVIEW→APPROVED; ASSIGNED_TO_BUYER→ASSIGNED; SOURCING…MANAGEMENT_VALIDATION→QUOTING; AWARDED→AWARDED; ORDERED…ORDER_CONFIRMED→ORDERED; IN_PRODUCTION…IN_WAREHOUSE→IN_TRANSIT; DELIVERED…PAID→RECEIVED; CLOSED; CANCELLED→CANCELLED (extra user status). |
| S2DR-15 | Minor | Roles; V4 `user_role` | New roles BUDGET_APPROVER and MANAGEMENT_APPROVER need the `Role` enum, any `user_role` role CHECK, and the "group-wide only for GROUP_MANAGEMENT/ADMIN" rule (S1) kept. | Migration plus a test that both roles must be company-scoped. |
| S2DR-16 | Major | Sprint size (14 AC) | Arabic for the whole app, rule and FX admin UIs, outbox and e-mail, one-tap, reminders with working-hours SLA and escalation, in-app notifications, tracker, versioned attachments and a backfill are more than a two-week slice. | Must keep: Arabic, circuit engine with rounds and question/return/reject/delegate, one-tap e-mail, inbox, tracker, e-mail outbox, reminders. If time runs short, cut in this order: (1) rule **edit** UI (keep API, demo seed, read-only list; editor in S3 with org admin); (2) escalation at 2×SLA (keep reminders); (3) in-app notification list (keep inbox badge); (4) attachment versions (keep upload/replace/delete); (5) FX admin UI (API + demo rates). Record cuts as carry-over, not silently. |
| S2DR-17 | Minor | API table | Gaps the UI will need: request detail `actions` for approvers; an inbox **count** for the badge; approval preview before submit ("Karim, then Leila"); attachment list in detail; admin absences for other users; rule versions; requester's open questions. | Add `actions` ⊇ {APPROVE, REJECT, RETURN, QUESTION, DELEGATE, ANSWER} to request detail; `GET /approvals/inbox/count`; `GET /requests/{id}/approval-preview`; `attachments[]` in detail; `GET/POST /admin/absences`; `GET /admin/approval-rules/{id}/versions`. |
| S2DR-18 | Minor | S2-AC-13 idempotency | The `Idempotency-Key` scope and the mismatch behaviour are unspecified. | Key per (user, method, path), 24 h; store the status and body hash; the same key with a different body → 422 `idempotency-key-reuse`; purge job. |
| S2DR-19 | Minor | S2-AC-06 absence | Delegation chains (A→B while B is also absent) and the eligibility of a delegate for `DEPARTMENT_MANAGER` / named-user stages are undefined. | Follow the chain to depth 3 with cycle detection, then fall back to escalation. Eligible = holds the stage role in the request's company (department-agnostic for DEPARTMENT_MANAGER), or is explicitly allowed by an admin. Validate on create and again at task creation. |
| S2DR-20 | Suggestion | S2-AC-07; v3.0 §12 | One tap for any amount weakens control on high-value requests. | Per-company `link_approval_max_amount` (default unbounded); above it, the e-mail shows only Review (sign-in). |
| S2DR-21 | Suggestion | S2-AC-10 dev mail | `.eml` files hold live approval links. | They live in git-ignored `BackEnd/storage/mail`; add a startup warning when `app.mail.mode=file` outside dev/test, and fail fast in production profiles. |
| S2DR-22 | Minor | Sprint 1 carry-over | S1CR-09 matters more now: the outbox claimer and the scheduler add new `TransactionLocks` callers. | Do S1CR-09 first in the sprint. |

## Answers to the review focus

- **ANY/ALL:** correct as written once S2DR-02/03/08/09 are added. Rejection or return by any approver ends the stage in both policies; ALL needs every task approved.
- **One-tap:** acceptable with S2DR-07. GET never acts; confirmation needs a user gesture. Link scanners that execute JavaScript still cannot POST without a click.
- **Rules and FX:** see S2DR-05/06. A request in the company currency needs no rate.
- **Outbox and SLA:** S2DR-09/10.
- **Attachments:** S2DR-11.
- **Arabic:** S2DR-13; `ar-TN` with Latin digits is the right choice for a Tunisia-based group.
- **Visibility:** S2DR-12.
- **API gaps:** S2DR-17.
- **Scope:** S2DR-16.
